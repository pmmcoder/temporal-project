## 1. 文档目的

本文档定义个人工作流平台 V1 的产品范围、功能需求、非功能需求和验收标准，作为架构设计、开发排期和测试验收的依据。实现方式见架构文档，本文档只描述“做什么”和“做到什么程度”。

## 2. 背景

当前仓库已用 Go 和 Temporal 验证了 Workflow、Activity、子 Workflow 和 Task Queue 的基本用法。下一阶段要在此基础上搭建一个**个人工作流平台**：平台提供基础服务，使用者只需用 Go 编写业务 Workflow 和 Activity 并注册，即可获得持久化执行、重试、定时调度、运行管理和飞书人工确认能力。

平台面向单台个人电脑和单一使用者，通过本地 Docker 部署。典型业务是**需要中途等待人工确认的长流程**和**AI / LLM 批处理**，但具体业务代码不属于平台范围。

## 3. 产品定位

个人工作流平台是一套运行在个人电脑上的 Temporal 基础服务，由四部分组成：

1. **Temporal 基础设施**：Temporal Server、PostgreSQL、Temporal UI 的一键部署、持久化和备份。
2. **Worker 运行框架**：业务代码的统一注册入口、默认超时与重试策略、日志、健康检查、优雅退出和测试脚手架。
3. **控制台**：自建 HTTP API 与 WebUI，负责 Workflow 目录、带校验的启动、运行管理、定时任务和待办审批。
4. **飞书人工确认组件**：Workflow 内调用一个函数即可发送飞书交互卡片并等待审批结果；附带通用飞书通知函数。

## 4. 目标与非目标

### 4.1 V1 目标

- 使用者只需编写 Go 业务代码并在一个入口注册，无需关心 Temporal 连接、Worker 生命周期和默认策略。
- 一条命令启动全部服务，重启后运行历史和定时任务保留 90 天。
- 在控制台查看 Workflow 目录，按输入 Schema 校验后启动，重复提交不产生重复运行。
- 查看运行列表和运行详情，执行取消、发送已声明的 Signal、再次运行。
- 创建和管理 Cron 定时任务。
- Workflow 可在执行中暂停等待人工确认，使用者可在飞书卡片或控制台待办页处理。
- 业务代码可发送飞书通知消息。

### 4.2 非目标

- 不内置任何具体业务 Activity（HTTP 请求、文件读写、LLM 调用、命令执行等），由使用者在业务代码中自行实现。
- 不支持通过页面、DSL 或拖拽定义 Workflow；Workflow 只能用 Go 代码定义。
- 不支持多用户、团队协作、权限角色和登录。
- 不暴露任何公网入站端口，不实现反向代理、隧道或 OAuth。
- 不重做 Temporal UI 的完整事件历史、堆栈和原始 Payload 查看能力。
- 不建设高可用 Temporal 集群，不支持跨机器部署，不支持多 namespace。
- 不支持业务代码与平台代码分仓发布。

## 5. 用户与使用场景

### 5.1 目标用户

唯一目标用户是拥有本机 Docker 环境、能编写 Go 代码、拥有飞书企业自建应用管理权限的个人开发者。

### 5.2 核心场景

1. 用户执行 `make up` 启动全部服务，打开控制台查看 Workflow 目录。
2. 用户在 `app/` 下新增一个业务 Workflow 并注册，执行 `make deploy` 后，目录中出现该 Workflow 及其输入表单。
3. 用户填写输入并启动；运行到需要确认的步骤时，飞书收到交互卡片，用户在手机上点击“通过”，Workflow 继续执行。
4. 用户不在飞书时，在控制台“待办”页处理同一审批。
5. 用户在运行列表查看状态，在详情页查看时间线摘要和 Activity 重试情况，必要时跳转 Temporal UI 深度排查。
6. 用户为某个 Workflow 配置 Cron 定时任务；电脑休眠恢复后，平台按补跑策略处理错过的执行。
7. 用户停止并重启全部服务后，运行历史、定时任务和等待中的审批都仍然存在。

## 6. 核心假设与约束

- V1 只支持单用户、单 namespace（`default`）、单 Temporal 集群、单应用 Task Queue（`personal-workflows`）。
- 业务代码与平台代码位于同一仓库，编译为同一个应用镜像；API 与 Worker 通过不同子命令运行。
- Temporal 是 Workflow 执行状态、运行历史、定时任务和审批状态的唯一事实来源；V1 不建立应用数据库。
- Temporal 持久化与 Visibility 使用 PostgreSQL。
- 运行历史保留期为 90 天；超过保留期的运行不可查询，其幂等键也随之失效。
- 宿主机只访问控制台和 Temporal UI，二者只绑定 `127.0.0.1`；Temporal Frontend 与 PostgreSQL 不映射到宿主机。
- 平台与外部的通信只有出站连接：飞书长连接和飞书 OpenAPI。
- Workflow 必须确定性执行；所有副作用必须放在 Activity 中。

## 8. 功能需求

### 8.1 Temporal 基础设施

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-INF-001 | P0 | 用户必须能用一条命令启动全部服务：PostgreSQL、Temporal Server、Temporal UI、控制台 API、Worker。 |
| FR-INF-002 | P0 | 首次启动必须自动完成数据库 Schema 初始化、namespace 保留期设置（90 天）和平台所需 Search Attribute 注册；重复启动必须幂等。 |
| FR-INF-003 | P0 | 平台数据（运行历史、定时任务、等待中的审批）必须在容器重建后保留，包括 `docker compose down`（不带 `-v`）后再启动、升级镜像版本、修改服务配置触发重建等场景。应用容器（控制台 API、Worker）及 Temporal、Temporal UI 必须无状态，可随时重建。 |
| FR-INF-004 | P0 | 所有服务必须配置健康检查和重启策略，并按依赖顺序启动。 |
| FR-INF-005 | P0 | 所有镜像必须固定到具体版本号，不得使用 `latest`。 |
| FR-INF-006 | P1 | 必须提供一条备份命令，将 Temporal 数据库导出到本地目录；并提供对应的恢复步骤说明。 |
| FR-INF-007 | P1 | 必须提供开发模式配置，允许在宿主机直接运行 Worker 连接容器内 Temporal，且该模式默认关闭。 |

### 8.2 Worker 运行框架

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-SDK-001 | P0 | 平台必须提供唯一的业务注册入口，业务代码通过它注册全部 Workflow 和 Activity。 |
| FR-SDK-002 | P0 | Workflow Type 和 Activity Type 必须使用显式注册名，不依赖 Go 函数名。 |
| FR-SDK-003 | P0 | 注册 Workflow 时必须提供 ID、显示名称、说明、示例输入；输入 Schema 必须由 Go 输入类型自动生成，不手写。 |
| FR-SDK-004 | P0 | 启动时必须检测并拒绝：重复的 Workflow ID 或 Activity 名称、不符合 Schema 的示例输入、不符合约定签名的 Workflow 函数。检测失败时进程必须退出并输出明确原因。 |
| FR-SDK-005 | P0 | 平台必须为 Activity 提供默认超时与重试策略：StartToClose 30 秒；重试初始间隔 1 秒、退避系数 2、最大间隔 1 分钟、最多 5 次。单个 Activity 可在注册时覆盖。 |
| FR-SDK-006 | P0 | 平台必须提供标记“不可重试错误”的方式，用于输入错误等重试无意义的场景。 |
| FR-SDK-007 | P0 | Worker 必须支持优雅退出：收到 SIGTERM 后停止领取新任务，等待进行中的任务在限定时间内结束。 |
| FR-SDK-008 | P0 | Worker 必须提供内部健康检查端点，反映与 Temporal 的连接和轮询状态。 |
| FR-SDK-009 | P0 | 平台必须提供测试脚手架：预注册全部定义的 Workflow 测试环境、审批组件 mock、基于导出历史的重放测试工具。 |
| FR-SDK-010 | P1 | Workflow 定义可声明允许接收的 Signal 及其载荷类型，载荷 Schema 自动生成。 |
| FR-SDK-011 | P1 | 平台必须提供子 Workflow ID 生成工具，保证同一父流程内的子流程 ID 确定且唯一。 |
| FR-SDK-012 | P1 | 构建流程必须包含 Workflow 确定性静态检查。 |

### 8.3 Workflow 目录

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-CAT-001 | P0 | 用户必须能查看所有已注册 Workflow 的 ID、显示名称、说明、输入 Schema 和示例输入。 |
| FR-CAT-002 | P0 | 控制台展示的目录必须与 Worker 实际注册的定义一致，同一次部署中二者不得出现差异。 |
| FR-CAT-003 | P1 | 不兼容变更必须通过新的 Workflow ID（如 `xxx.v2`）或代码内版本分支区分，不得静默改变已有 ID 的语义。 |

### 8.4 手动启动

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-TRG-001 | P0 | 用户必须能从目录选择 Workflow，提交 JSON 输入启动一次运行。 |
| FR-TRG-002 | P0 | 启动前必须按输入 Schema 校验，失败时拒绝启动并返回字段级错误。 |
| FR-TRG-003 | P0 | 启动成功必须返回 Workflow ID、Run ID 和 Temporal UI 链接。 |
| FR-TRG-004 | P0 | 启动请求必须支持幂等键。保留期内，相同幂等键且输入相同时返回已有运行；输入不同时返回冲突错误；无论已有运行是否结束，都不得创建第二个运行。 |
| FR-TRG-005 | P0 | 控制台发起的每次提交都必须自动携带幂等键，使重复点击和网络重试不产生重复运行。 |
| FR-TRG-006 | P0 | Temporal 不可用时必须返回明确错误，不得返回启动成功。 |
| FR-TRG-007 | P1 | 启动表单必须保留最近一次输入，便于再次执行。 |

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-RUN-001 | P0 | 用户必须能查看运行列表，按 Workflow、状态和时间范围筛选，并支持分页。 |
| FR-RUN-002 | P0 | 列表至少显示 Workflow 名称、Workflow ID、Run ID、状态、开始时间和结束时间。 |
| FR-RUN-003 | P0 | 系统必须区分以下状态：运行中、成功、失败、已取消、已终止、超时、已续接（continue-as-new）。 |
| FR-RUN-004 | P0 | 用户必须能查看单次运行的输入、输出、失败原因和时间线摘要。 |
| FR-RUN-005 | P0 | 用户必须能请求取消运行中的 Workflow；对已结束的运行必须返回明确的状态错误。 |
| FR-RUN-006 | P0 | 运行详情必须提供跳转 Temporal UI 对应运行的链接。 |
| FR-RUN-007 | P1 | 运行详情必须显示进行中 Activity 的重试次数和最近一次错误。 |
| FR-RUN-008 | P1 | 用户必须能向运行中的 Workflow 发送其定义中声明过的 Signal，载荷按 Schema 校验；未声明的 Signal 必须被拒绝。 |
| FR-RUN-009 | P1 | 用户必须能基于某次运行的输入，回到启动表单重新发起一次新运行。 |
| FR-RUN-010 | P1 | 不在当前目录中的运行（定义已删除或从 Temporal UI 启动）必须仍能显示，并标记为“未登记”。 |

### 8.6 定时任务

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-SCH-001 | P1 | 用户必须能为目录中的 Workflow 创建 Cron 定时任务，包含名称、Workflow、输入、Cron 表达式、时区和启用状态。 |
| FR-SCH-002 | P1 | 用户必须能编辑、暂停、恢复和删除定时任务。 |
| FR-SCH-003 | P1 | 保存时必须校验 Cron 表达式、时区和输入 Schema，无效时拒绝保存。 |
| FR-SCH-004 | P1 | 系统必须显示定时任务最近一次和下一次计划执行时间。 |
| FR-SCH-005 | P1 | 默认重叠策略为“上一次未结束则跳过本次”；默认补跑窗口为 1 小时，即服务停止或电脑休眠超过 1 小时错过的执行不补跑。两者可按任务覆盖。 |
| FR-SCH-006 | P1 | Workflow 定义升级后，已保存的输入不再符合新 Schema 的定时任务必须在列表中标记“需复核”，系统不得自动修改任务。 |

### 8.7 人工确认（审批）

| 编号 | 优先级 | 需求 |
| --- | --- | --- |
| FR-APR-001 | P0 | 业务 Workflow 必须能通过一个函数调用发起人工确认，并阻塞等待结果。请求包含标题、摘要、字段列表、是否允许备注、超时时间和超时处理方式。 |
| FR-APR-002 | P0 | 结果必须包含决定（通过、拒绝、超时）、备注、操作人、处理渠道（飞书或控制台）和决定时间。 |
| FR-APR-003 | P0 | 发起确认时，系统必须向配置的飞书会话发送交互卡片，卡片包含摘要、通过、拒绝和备注输入。 |
| FR-APR-004 | P0 | 用户必须能在飞书卡片中直接完成审批，无需打开控制台；平台不得为此开放任何公网入站端口。 |
| FR-APR-005 | P0 | 只有配置在审批人白名单中的飞书用户可以审批；其他人点击必须被拒绝并提示。 |
| FR-APR-006 | P0 | 控制台必须提供“待办”页，列出全部等待中的审批，并支持在页面上完成审批。 |
| FR-APR-007 | P0 | 同一审批的多次点击或飞书与控制台的并发操作，只以第一个有效决定为准；审批已处理后的操作必须提示已处理。两个操作几乎同时提交时，二者都可能先收到“已提交”，最终结果以卡片和控制台显示的终态为准。 |
| FR-APR-008 | P0 | 审批完成、超时或所在运行被取消后，飞书卡片必须更新为对应终态。 |
| FR-APR-009 | P0 | Worker 停止期间做出的审批决定不得丢失，Worker 恢复后 Workflow 必须按该决定继续。 |
| FR-APR-010 | P0 | 未配置飞书时，审批组件必须仍可工作，仅通过控制台待办页处理。 |
| FR-APR-011 | P1 | 超时处理方式支持“视为拒绝”和“使 Workflow 报错”两种。 |

#### 8.9.1 控制台与 Temporal UI 的职责边界

两个 UI 在运行列表、状态查看和取消上有意保留便利性重叠，但不形成两套等价的管理台。

| 能力 | 控制台 | Temporal UI |
| --- | --- | --- |
| Workflow 目录与业务说明 | 主要入口 | 不负责 |
| 结构化输入、校验与幂等启动 | 主要入口 | 仅通用启动能力 |
| 待办审批 | 主要入口 | 不负责 |
| 运行列表与业务状态摘要 | 主要入口 | 通用查询 |
| 取消与 Signal | 便捷入口（仅已声明 Signal） | 底层操作 |
| 定时任务 | 业务管理层 | Schedule 原生视图 |
| 完整事件历史、堆栈、原始 Payload | 仅摘要并跳转 | 完整展示 |
| Namespace、Task Queue 等运维查询 | 不负责 | 主要入口 |

## 9. 非功能需求

### 9.1 安全

| 编号 | 需求 |
| --- | --- |
| NFR-SEC-001 | 控制台和 Temporal UI 默认只绑定本机回环地址，不向局域网或公网开放。 |
| NFR-SEC-002 | 平台不得开放任何公网入站端口；与飞书的交互只使用出站连接。 |
| NFR-SEC-003 | 控制台 API 必须防御来自本机其他网页的跨站请求和 DNS rebinding：校验 Host 白名单，写请求校验同源 Origin 且只接受 JSON。 |
| NFR-SEC-004 | V1 不实现登录，但代码结构不得阻碍后续增加认证。 |
| NFR-SEC-005 | 审批卡片和通知内容会进入飞书和 Temporal 历史，平台文档必须提示业务代码不得放入密钥等敏感信息。 |

### 9.2 可靠性与持久化

| 编号 | 需求 |
| --- | --- |
| NFR-REL-001 | 控制台 API 重启不得导致已提交的 Workflow 或已做出的审批决定丢失。 |
| NFR-REL-002 | Worker 停止期间，已提交的任务保持待调度状态；Worker 恢复后继续执行，不得因等待 Worker 而超时失败。 |
| NFR-REL-003 | Temporal 或 PostgreSQL 重启后，Workflow 历史、定时任务和等待中的审批必须保留。 |
| NFR-REL-004 | API、Worker 和 UI 的故障相互隔离：API 停止不影响执行中的 Workflow，Worker 崩溃不影响控制台查询和飞书回调接收。 |
| NFR-REL-005 | 飞书长连接断开后必须自动重连，且不得导致 API 进程被判定为不健康而反复重启。 |

## 10. 数据与状态归属

| 数据 | 事实来源 | V1 处理方式 |
| --- | --- | --- |
| Workflow 定义与目录 | 代码仓库（`app/`） | 编译进镜像，API 与 Worker 读取同一份 |
| 运行状态、输入输出、历史 | Temporal（PostgreSQL） | 不复制；保留 90 天 |
| 幂等键与输入摘要 | Temporal（Workflow ID 与 Memo） | 不复制；随运行保留 90 天 |
| 定时任务 | Temporal Schedule | 通过 API 管理，不复制 |
| 等待中的审批 | Temporal（Workflow 状态与 Search Attribute） | 不复制 |
| 应用配置与密钥 | 环境变量与 `.env` | 不提交 |
| 最近输入等偏好 | 浏览器本地存储 | 丢失不影响功能 |

V1 不建立应用数据库。后续若需要收藏、标签或审计等 Temporal 无法自然表达的数据，再引入，并须明确与 Temporal 之间的事实来源划分。

## 11. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| Workflow 代码变更导致历史无法重放 | 运行中的 Workflow 在新 Worker 上报错卡住 | 显式注册名；不兼容变更用新 ID 或 `workflow.GetVersion`；重放测试纳入 `make test` |
| Activity 非幂等 | 重试产生重复副作用 | 平台文档要求业务 Activity 自行实现幂等；运行级幂等由平台保证 |
| 飞书长连接不可用或能力受限 | 无法在飞书内审批 | 审批始终可在控制台待办页完成；实现前核实飞书能力（见未决事项） |
| 电脑休眠或 Docker 停止 | 定时任务错过、Worker 长时间不在线 | Schedule 补跑窗口 1 小时；Activity 不设置 ScheduleToStart 超时 |
| 历史保留期到期 | 幂等去重失效、历史不可查 | 保留期 90 天写入文档与界面说明 |
| Temporal / PostgreSQL 升级失败 | 数据损坏或无法启动 | 版本固定；升级前执行备份 |
| Payload 过大 | 超出 Temporal 单个 Payload 和历史大小上限 | 文档提示业务代码传引用而非大文本，大数据由业务自行存储 |

## 12. 验收标准

V1 满足以下条件时视为达到 MVP 验收标准：

1. 在全新环境执行 `make up` 后，全部服务达到健康状态；namespace 保留期为 90 天，平台 Search Attribute 已注册。
2. 控制台目录中显示示例 Workflow，及其由 Go 类型生成的输入 Schema 和示例输入。
3. 提交合法输入后返回 Workflow ID、Run ID 和 Temporal UI 链接；Worker 执行完成，运行详情显示结果和时间线摘要。
4. 提交非法输入时拒绝启动并显示字段级错误。
5. 使用相同幂等键和相同输入重复提交，返回同一运行；相同幂等键不同输入返回冲突；已有运行结束后再次提交也不创建新运行。
6. 取消运行中的 Workflow 后，列表显示“已取消”；对已结束运行执行取消返回状态错误。
7. 审批示例运行后，飞书收到卡片；白名单用户在手机上点击“通过”，Workflow 继续执行，卡片更新为已通过；非白名单用户点击被拒绝。
8. 同一审批在控制台待办页完成后，飞书卡片同步更新为终态，再点击卡片提示已处理。
9. 停止 Worker，在飞书或待办页做出审批决定，再启动 Worker，Workflow 按该决定继续。
10. 创建、编辑、暂停、恢复和删除一个 Cron 定时任务，列表显示上次和下次执行时间。
11. 执行 `docker compose down` 后再 `make up`，运行历史、定时任务和等待中的审批仍然存在。
12. Temporal Frontend `7233` 和 PostgreSQL `5432` 无法从宿主机访问；控制台和 Temporal UI 只在 `127.0.0.1` 可访问。
13. 修改示例 Workflow 的注册信息并执行 `make deploy` 后，控制台目录与 Worker 注册保持一致。
14. `make test`（含重放测试）、`make lint`（含 Workflow 确定性检查）与 `make smoke` 全部通过。
